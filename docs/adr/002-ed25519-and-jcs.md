# ADR 002: Ed25519 signatures over RFC 8785 canonical JSON

- Status: Accepted
- Date: 2026-10-21

## Context

Agent cards, task envelopes and receipts are signed by one party and verified by another, and the two sides are written in different languages (Java and TypeScript). Both must produce identical bytes for the same document.

## Decision

- **Every agent has an Ed25519 key pair.** The private key never leaves its gateway. The platform stores only the public key: 32 raw bytes, base64url-encoded, the same form as a JWK's `x` member.
- **The key id is derived from the key:** the first 22 characters of the base64url SHA-256 of the encoded public key. It is computed the same way in `KeyIds.thumbprint` (Java) and `kidFor` (TypeScript).
- **Documents are signed over RFC 8785 (JCS) canonical JSON.** To keep both implementations simple and identical, signed documents may contain only safe integers. **Amounts are decimal strings** (`"125.00"`), never floats.
- **Tokens (grants and agent assertions) are compact JWS with `alg: EdDSA`.** Their `typ` is `pistiva-grant+jwt`, `pistiva-agent+jwt` or `pistiva-user+jwt`, so a token of one type cannot be passed off as another.
- **Shared test vectors keep the implementations in step:** the RFC 8032 key, its signature and kid, and a JCS sample. They live in `platform/.../CryptoTest.java` and `sdk/packages/agent-sdk/test/crypto.test.ts`.

## Consequences

- No crypto dependencies: both runtimes ship Ed25519.
- In development, keys are kept in encrypted files (scrypt + AES-256-GCM). Production needs KMS/HSM or OS keystore integration.
- A signature proves who signed a document, not that what it says is true (team document §8).
